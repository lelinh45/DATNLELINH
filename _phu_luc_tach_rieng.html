PHỤ LỤC A. TÀI LIỆU API CHI TIẾT

Phụ lục này mô tả đầy đủ các endpoint của hệ thống: phương thức, quyền yêu cầu, tham số và dạng kết quả trả về — đủ để một bên thứ ba tự tích hợp mà không cần đọc mã nguồn.

A.1. Nhóm xác thực (/api/auth)

EndpointMô tả
GET /api/auth/challenge?address=0x...Cấp thông điệp challenge có nonce ngẫu nhiên, sống 5 phút. Trả {success, challenge}. Địa chỉ sai định dạng → 400.
POST /api/auth/loginBody: {address, signature, challenge, deviceId, deviceLabel}. Xác minh chữ ký → JWT 24h. Thiết bị mới chưa duyệt → 403 kèm code DEVICE_PENDING. Challenge hết hạn/sai → 401. Chữ ký không khớp → 401.
GET /api/auth/pending?address=&deviceId=Thiết bị pending poll trạng thái duyệt: unknown / pending / active / revoked; khi pending trả kèm thông tin thiết bị đang hoạt động (deviceLabel) để UI chỉ rõ máy cần duyệt.
POST /api/auth/request-otpBody: {address, deviceId}. Gửi OTP 6 số về email chủ ví — chỉ khi ví không còn thiết bị nào khác đang hoạt động. Còn máy online → 403 OTP_BLOCKED; chưa có email → 400 NO_EMAIL; thiếu SMTP → 400 SMTP_MISSING; gửi lại sớm <60s → 429.
POST /api/auth/verify-otpBody: {address, deviceId, code}. Đúng mã → session active. Sai mã → 401 (tối đa 5 lần → 429); hết hạn → 400; còn thiết bị active → 403 OTP_BLOCKED.
GET /api/sessionsJWT. Liệt kê phiên thiết bị của ví đang đăng nhập.
POST /api/sessions/approveJWT của thiết bị cũ. Body: {address, deviceId}. Duyệt thiết bị pending của cùng ví.
POST /api/sessions/revokeJWT. Body: {sessionId}. Thu hồi một phiên — token của thiết bị đó chết ngay.

A.2. Nhóm tài liệu hệ thống

EndpointMô tả
POST /api/uploadJWT + NHẬP LIỆU+. Multipart field "document" (ciphertext, ≤25MB). Kiểm tra quota → pin IPFS. Trả {documentId, fileHash, ipfsCID, qrCode}. Hết quota → 403; lỗi Pinata → 500.
POST /api/verifyCông khai, rate limit 10/5phút/IP. Multipart: file + documentId. Trả {isMatch, isRevoked, revocationReason, currentFileHash, originalHash, differences, imageDiff, aiReport, message}.
GET /api/batchesJWT + requireViewer (rank ≥ 1 hoặc DB role NGƯỜI XEM+ACTIVE). Trả toàn bộ lô tài liệu (dùng để map docId → metadata, visibility); ví khách rank 0 chưa được cấp → 403.
POST /api/batchesJWT + NHẬP LIỆU+. Body {batchId, merkleRoot, ipfsCID, txHash, files[]}. Whitelist từng trường file; uploader lấy từ JWT. Lũy đẳng: batchId đã tồn tại → merge các trường còn trống (encKey, uploader "unknown") thay vì 409 — phục vụ retry và phục hồi metadata.
POST /api/batches/revokeJWT + QUẢN LÝ+. Body {docId}. Đồng bộ cờ isRevoked vào MongoDB sau khi đã thu hồi on-chain; tài liệu của ví ADMIN chỉ ADMIN được đồng bộ (khớp rule trên contract).
GET /api/documents/:docId/keyJWT. Trả khóa AES giải bọc: public → mọi ví đăng nhập; private → chỉ uploader (ADMIN cũng 403). Không có khóa → 404; không đủ quyền → 403.
POST /api/documents/:docId/visibilityJWT, chỉ uploader. Body {visibility: 'public'|'private'} — đổi chế độ hiển thị sau khi đã tải lên. File đã thu hồi → 409; không phải chủ sở hữu (kể cả ADMIN) → 403.
GET /api/documents/:docId/statusCông khai. Trả {isRevoked, revocationReason, visibility, uploader} — dữ liệu đã public on-chain.
GET /api/documents/lookup?hash=&name=Công khai. Tra tài liệu theo hash nội dung, tên file đúng/docId, và gợi ý tên tương tự — trả {byHash, byName, bySimilar}.
POST /api/documents/lookup-similarCông khai. Body {chunks: [hex64,...]} — so tập chunk-hash (fuzzy hash theo đoạn, CTPH) với các file đã lưu, trả {matches: [{docId, fileName, score,...}]} gồm các bản ghi trùng ≥40% đoạn, xếp theo % giảm dần.

A.3. Nhóm ví và quản trị

EndpointMô tả
GET /api/wallets/meJWT — mọi rank. Hồ sơ của chính ví đăng nhập (alias, email, phone, requestedRole).
GET /api/wallets/pendingJWT + ADMIN. Danh sách ví status ACTIVE nhưng rank on-chain = 0 — khay "chờ cấp quyền".
GET /api/walletsJWT + requireViewer. Danh sách ví; storageUsed do server tính lại từ Batch — giá trị client tự khai bị bỏ qua; email/phone bị che với caller rank < QUẢN LÝ.
POST /api/wallets/syncJWT. Cập nhật ví: field tự sửa chỉ {alias, lastActive, requestedRole} — requestedRole chỉ nhận NHẬP LIỆU/QUẢN LÝ/NGƯỜI XEM; {role, status, storageLimit, roleGranted} chỉ ADMIN và chỉ cho ví người khác.
POST /api/wallets/rejectJWT + ADMIN. Body {address}. Từ chối ví chờ duyệt: đánh dấu rejected trong hồ sơ; ví bị từ chối khai báo lại thông tin thì quay về trạng thái chờ.
POST /api/wallets/emailJWT. Đăng ký/đổi email + SĐT chủ ví (email nhận OTP, SĐT làm liên hệ cảnh báo). Email hoặc SĐT sai định dạng → 400.
POST /api/apikeysJWT + ADMIN. Body {name}. Trả {key: "sk_live_..."} đúng một lần — server chỉ lưu hash.
GET /api/apikeysJWT + ADMIN. Danh sách key (không chứa plaintext): name, createdBy, revoked, lastUsedAt.
POST /api/apikeys/:id/revokeJWT + ADMIN. Thu hồi key — có hiệu lực ngay.
GET /api/notificationsJWT. Danh sách thông báo của ví đang đăng nhập (duyệt thiết bị, ví mới, cảnh báo).
POST /api/notifications/readJWT. Body {id} — đánh dấu thông báo đã đọc.

A.4. Nhóm đối tác (/api/v1) — xác thực header x-api-key

EndpointMô tả
POST /api/v1/documentsMultipart "document" (plaintext, ≤25MB). Server mã hóa AES → IPFS → on-chain → trả {success, documentId, fileHash, ipfsCID, txHash}. Quá 60req/phút → 429; hết quota → 403; lỗi ghi chain → 502.
POST /api/v1/verifyFile + documentId → {success, match, documentId, isRevoked, timestamp}.
GET /api/v1/documentsDanh sách tài liệu của chính key: docId, fileName, fileHash, fileSize, ipfsCID, txHash, isRevoked, createdAt.
GET /api/v1/documents/:docId/downloadFile gốc đã giải mã; tài liệu của key khác → 404 như không tồn tại (không lộ sự tồn tại).

Mã lỗi chung: 400 dữ liệu sai định dạng · 401 thiếu/sai xác thực · 403 không đủ quyền hoặc hết quota · 404 không tồn tại · 413 file quá 25MB · 429 vượt rate limit · 500/502/503 lỗi máy chủ hoặc dịch vụ ngoài.

B.1. Cấu trúc bản ghi tài liệu trên chuỗi

TrườngKiểuÝ nghĩa

timestampuintThời điểm ghi (block time) — bằng chứng thời gian

B.2. Schema các collection (trường đáng chú ý)

CollectionTrường quan trọng và ràng buộc
Walletaddress unique lowercase; status ∈ {ACTIVE, REVOKED, DELETED}; role ∈ {ADMIN, QUẢN LÝ, NHẬP LIỆU, NGƯỜI XEM, BỊ KHÓA, ĐÃ XÓA}; roleGranted bool — chỉ true khi admin đã cấp quyền (gate cho fallback role khi RPC lỗi); rejected bool cho ví bị từ chối; requestedRole ∈ {NHẬP LIỆU, QUẢN LÝ, NGƯỜI XEM, null}; storageLimit mặc định 1024MB; email định dạng RFC
BatchbatchId unique; uploader = địa chỉ JWT; files[].visibility ∈ {public, private} mặc định private; files[].encKey dạng "iv:ct:tag"
DeviceSession(address, deviceId) unique; status ∈ {pending, active, revoked}; otpHash "salt:scrypt"; otpExpires epoch ms; otpAttempts ≤ 5
ApiKeykeyHash unique (sha256 của token); revoked bool; createdBy = địa chỉ ADMIN
PartnerDocumentdocId unique; apiKeyId → ApiKey; fileSize theo bytes; encKey bọc GCM; txHash giao dịch ghi
Notificationtype ∈ {device_pending, device_approved, new_device, new_wallet, doc_revoked, session_revoked, system, security_alert}; meta chứa deviceId hoặc địa chỉ ví mới
AuthChallengeaddress key; challenge chuỗi có nonce; expiresAt TTL index tự xóa

B.3. Chuỗi mã hóa và định dạng lưu trữ

  • encKey (escrow): iv_hex : ciphertext_hex : authtag_hex — AES-256-GCM, iv 12 byte ngẫu nhiên mỗi lần bọc.
  • otpHash: salt_hex : derivedkey_hex — scrypt N mặc định, keylen 32, salt 16 byte.
  • API key: token plaintext dạng sk_live_<48 hex> hiện một lần; DB chỉ giữ sha256 hex 64 ký tự.
  • fileHash: sha256 hex 64 ký tự, tính trên byte gốc trước mã hóa.
  • documentId: <tên file đã lọc>_<epoch ms>, tên lọc ký tự lạ tối đa 100 ký tự.

C.2. Checklist kiểm thử tay trước demo

  • Đăng nhập MetaMask ví NHẬP LIỆU → upload file private và public → đổi ví khác kiểm tra ổ khóa và quyền tải.
  • Kéo-thả nhiều file vào dropzone Đóng Dấu (viền sáng khi kéo qua) → xóa từng file bằng nút ✕ → kéo-thả 1 file vào dropzone Xác Thực; thả nhầm ra ngoài trang không bị mở file thay tab.
  • Ví mới đăng nhập lần đầu → phòng chờ khai alias/email/quyền mong muốn → admin thấy ví trong khay chờ → bấm Duyệt (form tự bung + cuộn + nháy sáng) → Thực thi ký assignRole → bảng ví tự cuộn tới dòng vừa duyệt.
  • Đăng nhập trên trình duyệt/thiết bị khác → thấy thông báo pending ở thiết bị cũ → duyệt hoặc từ chối → kiểm tra phiên bị chặn.
  • Đăng ký email ví → xin OTP → nhập đúng/sai → quan sát đếm lỗi và cooldown gửi lại.
  • Verify file gốc, file sửa 1 ký tự, file đã thu hồi — đối chiếu thông báo và AI report.
  • Xem trước từng loại: PDF, ảnh, văn bản, DOCX — kiểm tra tab mới và layout.
  • Bấm link PHÍ (ETH) → mở đúng giao dịch trên sepolia.etherscan.io.
  • ADMIN tạo API key → copy → curl upload/verify/list/download → thu hồi → curl lại → 401.
  • Thu nhỏ cửa sổ trình duyệt kiểm tra cuộn ngang bảng và cắt tên file.
